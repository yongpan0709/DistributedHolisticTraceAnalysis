# PP/VPP 局部降速如何影响整体耗时

## 问题与结论

相同 Megatron/MUSA 代码运行在不同 2k 集群机器上，出现了性能差异。DHTA 定位到部分 PP stage、部分 microbatch 的 forward 偏慢。由于流水线存在交错执行和相互等待，局部耗时的减少不会必然等量转化为整体收益。

本分析采用**固定 DAG 上的最长路径动态规划与逐轮反事实评估**：先确定节点有依据的目标耗时，再重新计算全图最长路径，评估收益及瓶颈接替。

## 1. 从事件到 DAG

固定一次运行、一个 iteration、一个 PP group 后，用四元组标识节点：

\[
v=(\mathrm{PP\ stage},\mathrm{VPP\ stage},\mathrm{microbatch},\mathrm{FWD/BWD}).
\]

实现中使用 `(rank, direction, microbatch, vpp)` 作为键，再映射到整数 `node_id`。耗时是节点属性，修改耗时不改变节点身份。原始 DHTA 的 `ts/dur` 单位为微秒，分析内部转为毫秒。

构图规则为：

- 同一 rank 的计算事件按观测时间排序，添加相邻执行依赖。
- 同一 microbatch/VPP 的 forward 沿物理 PP 顺序连接，backward 反向连接。
- 添加跨 VPP 的首尾连接，以及同一任务的 forward → backward 依赖。

物理 PP 顺序按 rank 升序确定，VPP 编号从 1 连续开始。输入需覆盖完整 PP group 中相同的 microbatch/VPP 集合，程序检查重复、缺失和环。调度语义不符合这些约定时，需要修改构图规则。

## 2. 核心解法

按拓扑顺序计算各节点最早完成时间：

\[
F(v)=d_v+\max_{u\to v}F(u).
\]

根节点使用原始释放时间作为开始时间。记录使最大值成立的前驱，再从最晚完成的终点回溯，得到关键路径的节点列表。一次最长路径求解需要 O(V+E) 次节点/边处理。

记原始路径长度为 \(L_p\)，其中包含固定的根起点偏移；节点可缩短量为 \(x_v\)。更新全部路径后，模型收益为：

\[
\boxed{\Delta T=\max_p L_p-\max_p\left(L_p-\sum_{v\in p}x_v\right)}.
\]

例如，两条路径原长为 100 ms 和 90 ms。仅将第一条路径独有节点缩短 20 ms 后，两条路径变成 80 ms 和 90 ms；整体只缩短 10 ms，因为第二条接替成为关键路径。

每轮处理当前代表关键路径上的可优化 forward，保留此前修改并全图重算。backward 始终不变。若旧路径更新后的长度等于新最长路径长度，则本轮沿旧路径的缩短量全部转化为模型收益；不要求两次返回的路径列表相同，因为可能存在并列路径。

达到轮数或不同路径数上限，或当前路径已无符合规则的 forward 时停止。零收益轮次仍可继续处理并列瓶颈。不同轮次的路径可能重复，因此不能保证找到任意指定的 N 条不同路径。

## 3. 0804 案例

2026 年 8 月 4 日，在 2048 卡规模上开展了一次性能实验。实验前没有影响性能的功能变更上线，因此在当时的运行环境下采集了 PyTorch Profiler traces，并据此进行了详细的性能问题排查。以下使用该次实验的 trace 分析 PP/VPP 关键路径及局部 forward 加速的潜在收益。

选择 PP36、iteration 19，包含 32 个物理 PP stage、2 个 VPP stage、48 个 microbatch：

| 项目 | 数量 |
|---|---:|
| 计算节点 | 32 × 2 × 48 × 2 = **6,144** |
| 去重依赖边 | **15,184** |
| 初始关键路径节点 | **250**，其中 125 个 forward、125 个 backward |
| 初始关键路径上 >50 ms 的 forward | **54**，其中 rank804 占 51 个 |

rank804 的这 51 个 forward 全部 >70 ms。以 50 ms 为参考，54 个节点的累计超额耗时为 1.805022 s，其中 rank804 占 1.792968 s，约 99.3%。该比例只描述所选路径上的超额耗时分布。

按“每轮当前关键路径上的 forward >70 ms →50 ms”执行：

| 轮次 | 本轮修改 forward 数 | 原路径预计缩短 ms | 全图模型收益 ms | 累计模型收益 ms |
|---|---:|---:|---:|---:|
| 1 | 51 | 1792.967825 | **1687.281666** | 1687.281666 |
| 2 | 4 | 102.669331 | 26.243879 | 1713.525545 |
| 3 | 2 | 67.103967 | 47.212300 | **1760.737845** |

第一轮，原路径更新后的耗时为 **19.140902 s**，但全图新的最长路径为 **19.246588 s**。所以实际模型收益是 20.933870 − 19.246588 = **1.687282 s**，而不是沿原路径累加得到的 1.792968 s。

这也复现了此前“将 rank804 全部 88 个 >70 ms 的 forward 设为 50 ms”的首轮整体模型收益；此次仅修改其中位于初始关键路径上的 51 个。三轮累计修改 57 个 forward，模型耗时降至 **19.173132 s**，记录到 4 条不同代表关键路径。

## 4. 适用范围与进一步优化

当前节点权重来自 DHTA 的 GPU kernel span，可能包含内部空隙和通信；它不是独立的纯计算服务时间。根起点保留，其他节点按依赖就绪尽早执行，边延迟为零。模型尚未完整覆盖通信等待、资源竞争、跨 PP group 同步和训练尾部阶段。

在 0804 中，简化计算模型终点为 20.933870 s，观测最后一个 forward/backward 结束于 21.340493 s。原始时间戳还存在 4 处与构造依赖轻微冲突的位置，最大约 0.2234 ms。程序保留依赖并报告冲突；模型精确求解不代表物理预测已被验证。

历史敏感性试算中，对未解释等待采用不同固定方式，曾得到约 15.878 ms 或 0 ms 的模型收益。这些也不是更可信预测或实际收益下界，说明不能仅靠粗粒度 trace 唯一确定反事实收益。

已知目标耗时时，拓扑动态规划即可求解。若需要在预算下自动选择“优化哪些节点、分别缩短多少”，固定 DAG、连续可缩短量和线性成本可建模为 LP；若还要改变 stage 划分、设备分配或任务顺序，则需要另外定义调度优化问题。当前逐轮规则不提供预算下的全局最优保证。

实际使用时，目标耗时应来自同 stage 同工作量的正常样本或实验。优化后需确认节点真的加速，并用新 trace 检查依赖、等待和端到端效果；若执行顺序或资源约束改变，需要重新构图。
